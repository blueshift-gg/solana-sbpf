solana-sbpf · simd-experiment · BLAKE3

Virtual vector registers, lowered to AVX2

sBPF gained 13 experimental vector instructions, a 2 KiB vector region at 0x6_0000_0000, and a JIT that turns each one into native AVX2. On BLAKE3 at 1 MiB, the register-cached JIT is 17.2× faster than scalar sBPF in the JIT under Rosetta 2 (25.8× under QEMU) and uses 19.5× fewer CUs. All x86 numbers below come from translated or emulated hardware, not a real Intel CPU.

Research questions

What the measurements say

How much faster is BLAKE3 with native SIMD instead of scalar sBPF?

LargeUnder Rosetta 2, 17.2× at 1 MiB with the 8-way kernel and register caching, and 11× without caching (QEMU: 25.8× and 14.7×). Messages under 8 KiB use the single-state kernel and gain a more modest 2.3–2.7×. QEMU showed 9× at 64 B because its scalar JIT code runs disproportionately slowly. Scalar sBPF suffers because every load and store in this JIT is a host call, and the 16-word state doesn't fit in sBPF's 10 registers.

How much memory traffic does register residency remove?

Most of itIn the microbenchmark, the cached loop body has one load and one store per basic block, where the direct version has one of each per op. On the full hash program, caching removes 58% of loads and stores for the 8-way kernel and 92% for the single-state kernel. Under Rosetta 2 that makes it 1.57× and 1.63× faster than uncached, and 2.1× faster per op in the microbenchmark loop.

Does a dedicated vector region beat ordinary VM memory?

YesThe same program with its vector file in the heap (C) is only 1.27× faster than scalar and 8.6× slower than the region (D) under Rosetta 2. Each memory-mode op pays a host call to translate and bounds-check its operands. Static slot addresses also make register caching possible in the first place.

Can it approach native host BLAKE3?

PartlyUnder Rosetta 2, native BLAKE3 (also translated) is still 5.4× faster than the best sBPF variant, and 2.7× under QEMU. The remaining gap comes from flushes around the 16 message loads per block, two transposes, spills (32 live vectors on 15 YMM registers) and scalar tree logic.

Is the complexity justified compared with a syscall?

Not measuredNo sol_math-style syscall was built, so this report makes no syscall claim. The cache's coherence rules caused two JIT crashes during the experiment, both from scratch-register tracking. That cost is real and ongoing.

Environments and method

Where these numbers come from

  • macOS Rosetta 2 (M3 Max, x86_64-apple-darwin build) is the primary environment and runs every variant. It executes AVX2 but hides it from CPUID, so the harness sets simd_assume_avx2 when sysctl.proc_translated is 1. Rosetta splits each 256-bit op into 128-bit NEON ops, so absolute SIMD speed will differ on real Intel or AMD hardware.
  • QEMU 7.2 -cpu max runs in an arm64 Linux container on an Apple M3 Max. It also runs every variant. CPUID reports AVX2, so no override is needed. It's about 10× slower than Rosetta for scalar code, and AVX2 is emulated with helper functions, which likely understates the SIMD gains.
  • Rosetta for Linux ("VirtualApple", Docker linux/amd64) gives the most realistic x86 timing for the interpreter and the scalar JIT. It doesn't implement AVX: any ymm instruction raises SIGILL, so the SIMD JIT variants can't run there.
  • Native arm64 (macOS, M3 Max) provides interpreter-only reference numbers. There is no arm64 JIT here.
  • Each value is the median of up to 15 samples. Each sample batches enough runs to last at least 2 ms, and every run is warm. Inputs are identical for all variants, and every benchmark checks its digest against blake3::hash.
