Vector intrinsics without a new opcode

Every vector operation can also be written as an ordinary static syscall in the style of sol_multi3 (SIMD-0645), so the bytecode stays plain eBPF. The JIT recognizes the call and inlines the same AVX2 code as the opcode form. On a Zen 4 EPYC, BLAKE3 at 1 MiB runs 34× faster than scalar sBPF with intrinsic calls, against 51× with the dedicated opcode.

Two encodings, one lowering

What the program contains

A · scalar sBPF, JIT

BLAKE3 in ordinary 32-bit sBPF instructions. The baseline.

E · opcode form, register-cached JIT

Vector slots live in a 2 KiB region at 0x6_0000_0000. The JIT keeps them in ymm0–ymm14 within a basic block.

G · intrinsic calls, register-cached JIT

The same program and the same lowering, written as mov64 r5 + call sol_<op>. Each call also sets r0 = 0.

F · native blake3 crate

The host's hand-tuned SIMD implementation, shown only as a reference ceiling.

Full hash throughput

MiB/s by input size

Below 8 KiB the program runs the single-state kernel, where G and E are identical. From 8 KiB it switches to the 8-way kernel, where G falls behind. See the next section.

Speedup over scalar sBPF in the JIT

Where the call form costs something

Why the 8-way kernel is slower as calls. Each vector op is identical AVX2 in both forms. The call form adds a masked mov r9, imm + add r9, key for mov64 r5 and a mov eax, 0 for the r0 result. That's about 22 extra bytes per op.

The 8-way compression routine is one huge straight-line block, and it grows from 26 KB to 48 KB of machine code. That overflows Zen 4's 32 KB L1 instruction cache, so the loop becomes front-end bound. The small kernels fit either way: the microbenchmark and the single-state kernel run at exactly the same speed in both forms.

Fix (not yet implemented): skip emitting r5 and r0 when the next instruction overwrites them before anything reads them. Within a block that is almost every intrinsic call. That would bring G's code back to E's size.

What the JIT emitted

Zero intrinsic calls fell back to a syscall: the JIT resolved every operand at compile time. Vector loads, stores and cache hits match between the two forms. The only difference is the added scalar instructions.

CU consumption

Simulated compute units per hash

The call form costs 2 CUs per vector op (mov64 + call), against 1 for the opcode. Scalar code between vector ops is unchanged. Per-op CU pricing is provisional.

Method

How it was measured

  • Each value is the median of 15 samples. Each sample batches enough warm runs to last at least 2 ms. JIT compile time is the median of 7 cold compiles.
  • Inputs are identical for every variant, and each benchmark checks its digest against blake3::hash.
  • TSC ticks come from rdtsc at about 2.75 GHz; cores boost higher, so ticks aren't core cycles.
  • No sol_math-style batched syscall was built, so there is no comparison against one.
